# 0008. FMU builds: one fmu_build tool, supervised build jobs, build.json provenance

- Status: Accepted
- Date: 2026-10-10

## Context

Claude can create FMUs. Authoring stays out of the tools: Claude writes the source with its own Write and Edit tools, so the user sees every file in the write prompt, and MCP tools only check, build and run. The facts that shape the build:
- **pythonfmu** (spike (e)) builds FMI 2.0 Co-Simulation only, by importing the source as a module to read its `Fmi2Slave` class. The FMU bundles pythonfmu and runs in our Python-hosted engines without `LD_PRELOAD`.
- **OpenModelica `omc`** (spike (f)) exits 0 on every failure, prints errors only through `getErrorString()` (with harmless `Error:` lines even on success when offline), writes seven side files into its working directory, offers FMI 2.0 only, integrates CS with forward Euler unless built with `--fmiFlags=s:cvode`, and needs a writable `HOME`. A toy model takes 6 to 20 s; large models take minutes.
- Some clients (Claude Desktop) cancel a stdio tool call after about 60 s, so a long build can't run inside the call.
- Building executes the user's code: pythonfmu imports it, and omc can evaluate functions and compile external C.

Options considered: two tools (`fmu_build_python`, `fmu_build_modelica`; rejected: one entry point and one result shape are simpler for Claude); a synchronous subprocess inside the tool call (rejected: long builds); a separate build worker, queue or run kind with its own tools (rejected: runs already have spawn, heartbeat, timeout, stop, takeover, admission and listing).

## Decision

**One tool, `fmu_build(source, name?, overwrite?, wait_s?)`.** `.py` builds FMI 2.0 Co-Simulation with pythonfmu; `.mo` builds FMI 2.0 ModelExchange plus CoSimulation with omc (`version="2.0"`, `fmuType="me_cs"`, always `--fmiFlags=s:cvode`); other extensions are refused. Later phases may only add optional parameters. One module, `build.py`, branches on the extension; there is no backend class or registry.

**A build is a job in the run store.** It takes an ordinary run ID, its `spec.json` is a `BuildSpec` (`kind: "build"`), and the ordinary worker (`afmi worker <dir>`) runs it by dispatching on `kind`. Heartbeat, `max_workers` admission, takeover, `run_stop` and the watchdog work unchanged; the timeout is `Timing.build_timeout_s` (30 min). `fmu_build` validates, claims the job and waits up to `wait_s` (default 45 s, capped at 60 s): a build that finished returns its result, a failed one raises its diagnostics as a `ToolError`, and a running one returns the run ID. `run_status`, `run_list` (with `kind`) and `run_stop` serve builds; there are no new tools.

**Validation before any job or subprocess.** The source resolves (symlinks too) inside the workspace, outside the store and `generated/` (an outside path is refused without revealing whether it exists), is a regular UTF-8 file of at most 256 KiB, and the server reads it once and hashes it. A `.py` must contain `Fmi2Slave`, and its stem must be an identifier that is no keyword, not in `sys.stdlib_module_names` and not importable (`find_spec`), because pythonfmu and the FMU's host import it by that name. A `.mo` stem must be a Modelica identifier (it names the class to build), the file must define a `model` or `block` of that name (a text search, not a parse), and `omc` must be on `PATH` (else an install hint). `name` (default: the stem) matches `^[A-Za-z][A-Za-z0-9_]{0,63}$`, isn't a Windows reserved name, doesn't collide with an existing `generated/` entry by case only, and isn't being built by another job.

**Isolation, not a sandbox.** The worker builds from a private copy of the hashed bytes (`runs/<id>/source/`) in `runs/<id>/work/` (cwd and `TMPDIR`, removed afterwards), so nothing appears next to the source. The tool runs with argv only (`sys.executable -I -B -m pythonfmu build ...`, or `omc` on a `.mos` we generate with `setModelicaPath` pinned), stdin from `/dev/null`, output to `runs/<id>/build.log`, and an allowlisted environment (`PATH`, `HOME`, `LANG`, `OPENMODELICA*`, fixed `PYTHON*` values, our `TMPDIR`). It stays in the worker's process group, so the watchdog's and the supervisor's group kills reach it. We never call `pythonfmu deploy`, `installPackage` or `updatePackageIndex`, and ruff TID251 bans importing `pythonfmu` in `src/`. This is not a sandbox: the tool runs as the user, with network access. The trust boundary is the user reviewing the file and approving the `fmu_build` call. One exception keeps omc's own downloads out: omc alone gets `http_proxy`, `https_proxy`, `HTTP_PROXY` and `HTTPS_PROXY` set to the unroutable `http://127.0.0.1:9` and `no_proxy` empty, so its libcurl can never fetch a package index or library (on a fresh `HOME` the log shows one failed download, which the parser drops; a warm `HOME` makes no attempt). Compiled model code and external C aren't restricted.

**Outputs and atomicity.** Success decides from the tool's own result (pythonfmu: exit 0 and one `.fmu`; omc: the path `buildModelFMU` returned), then the FMU's `modelDescription.xml` is checked. With the watchdog disarmed and under the store lock, the worker re-checks the output directory and writes `generated/<name>/<name>.fmu`, then `build.json` (a `BuildRecord`), each through a temporary file in the same directory and `os.replace`, and a copy of the record in `runs/<id>/build.json`. Then it appends one `fmu_built` event and writes `finished`. A failure, stop or timeout leaves `generated/` unchanged and appends no `fmu_built` event. `overwrite=true` replaces only a directory that holds a readable `build.json`, and the result reports the replaced sha256.

**Protocol (additive, still v1).** `BuildSpec`, `BuildRecord` and `BuildEvent` (`type: "fmu_built"`, with `run_id`, `fmu_path`, `fmu_sha256`) are new documents with schemas in `docs/schemas/`; `ErrorCode.BUILD_FAILED` and `IndexEntry.kind = "build"` are new values. Run specs and run events are unchanged.

**Diagnostics.** A failed build's text is at most 2000 characters: a count line, at most 10 lines `path:line[:col]: error: message` (warnings likewise), errors first, with the source's workspace-relative path and no temporary path, traceback frame of pythonfmu or importlib, or ANSI escape; then the store path of `build.log`.

## Consequences

- (+) Builds of any length survive the 60 s cutoff, and stop, timeout, crash and takeover reuse tested code. Claude gets compiler errors it can fix with a small edit.
- (+) Every FMU in `generated/` carries its provenance (source hash, tool versions, options, FMU hash), and the pane can read it without parsing XML.
- (-) Builds count toward `max_workers` and compile inside the run store: keep the store on a Linux filesystem (`/lab` or `AFMI_STORE_DIR`), or builds on the Windows bind mount are slower.
- (-) A build's `status.json` reuses the run fields: `t_start = t_stop = t = 0`, `progress` 0 until it finishes. `fmu_build` publishes no output schema (the `tools/list` budget); its result has `RunView`'s shape.
- (-) pythonfmu FMUs need, wherever they run, the same CPython minor version (3.12), the slave's own imports, and in a non-Python host `LD_PRELOAD` of `libpython3.12.so`. omc FMUs are linux64 only and carry their C sources.
- (-) A worker killed in the microseconds between the two `os.replace` calls leaves an FMU whose `build.json` is missing or stale; readers compare `fmu.sha256`.
- (-) If the worker dies by itself (a crash or an outside SIGKILL), the build tool can be orphaned: it stays in the worker's process group, and the supervisor only kills the group of a *live* pid. A stop, a timeout or the takeover of a hung worker kill the group while the worker lives, so only an unprompted death leaves a tool behind. A fix is planned.
- (-) Two servers on one store can, for a moment, both start a build of one name: the same-name check and the ID claim run under the per-server `admission` lock, as the `max_workers` check does. The commit re-checks the output directory under the store lock, so without `overwrite` the later build fails cleanly instead of replacing the earlier one.
- Follow-ups: concurrent first-time omc library installs into one `HOME` are untested; a warm `loadModel(Modelica)` made no network attempt in B2, and the offline proxy would fail one fast; a named volume for `~/.openmodelica` (saves a 154 MB copy per recreated container) needs an image rebuild that creates the mount point as user `dev`, so it waits for the next planned rebuild.
